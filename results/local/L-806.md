# L-806: LOAD-009 splitting at scale (Phase A, 1M docs on the box)

Setup: es717-plain 7.17.29, 1,000,000 `load-logs` docs (edgen `logs`, seed 1, 1,012 MB NDJSON). Run with
`scripts/load/split.py L1L` (limit 1000). The spec's 10M values are run as written: 256 MB gives 4 parts and
`--maxRows 1000000` gives 1 part. Scaled values (raw/40 bytes ≈ 25.3 MB, and docs/10 or 3×docs/10 rows) exercise
many boundaries.

**Result: PASS.** 13 cases and 4 extras, with no failures.

Checks that passed in every case:

- **Part names and files:** names are contiguous, and there are no extra files.
- **No document spans parts:** every part ends with a newline, and every line is a whole JSON document with an
  `_id`.
- **Part size:** each part is ≤ the limit plus its last doc, and every part but the last reaches the limit.
- **Part count:** the count matches `ceil(docs/maxRows)`, or a replay of the byte rule over the reference order.
- **Docs and digest:** the docs total 1,000,000, and an edverify digest of all parts equals the index's.
- **Staging (BRK-RES-002):** during each run, the output directory was polled every 20 ms (96–607 polls per case).
  A visible part appeared only in the commit window, when all parts were already staged. The commit is a sequence of
  renames that lasted at most 15 ms for 40 parts.

## Extras

- **Restore all parts:** each part was restored with its own invocation (`--concurrency 8`), then diffed against the
  source.
  - Plain 40 parts: 36.1 s, 1,000,000 docs, digest-equal.
  - zstd 10 parts: 33.0 s, 1,000,000 docs, digest-equal.
- **kill -9 mid-split** (with 15 parts staged): no part became visible. The `--overwrite` rerun exited 0 with 40 parts
  and was digest-equal. The killed run's 15 hidden staged files were left behind, and the rerun logs a leftovers
  warning.
- **`--overwrite` with fewer parts** (10 over 40): the new set is digest-equal. The 30 older parts, `p.split-10…39`,
  were left in place, and the WARN names them.
- **Leaks:** no `.part-` files were left outside the kill case. One scroll context was still open at the end. It was
  most likely the kill -9'd dump's, because a killed process cannot clear its scroll, and the context stays open until
  its `--scrollTime` runs out.

## Findings for the lead (no code change)

- **No tool bug was found.** The first L0 dev run flagged parts as visible before exit, but that was the harness
  catching the commit window. The assertion now requires staged + visible to equal the final count whenever any part
  is visible.
- **`--fileSize` counts uncompressed line bytes, without newlines.** As a result, gzip and zstd parts are far smaller
  on disk than the limit, and part boundaries are the same for all codecs.
- **`--maxRows 1000000` on 1M docs gives one `p.split-0.json`,** the same as Node.
- **Files staged by a run killed with kill -9 are left in place,** as decided in D-5 (L-648). The rerun warns about
  them.
- **Older parts stay after `--overwrite` with fewer parts.** They are left with a warning, so a glob read-back would
  mix the two sets. This is documented behavior, but worth a README note if the lead wants one.
