# L-802a: allocator study for the LOAD-005 memory growth

Engine es717-plain (Elasticsearch 7.17.29, 2 GB heap) on the shared box; `scripts/load/allocbench.py`, ~1 KB `logs` docs,
`--concurrency=8 --limit=5000`, sliced dump `--slices=4`. 100k and 1M: 3 reps (median, min–max); 10M: 2 reps (rep0 / rep1),
rep2 stopped for time (needs a dedicated load host). Peak RSS = the child's own `VmHWM` (not `ru_maxrss`, which includes
the Python driver because of vfork). Plateau = memcheck rule (second-half peak at most 10% above the first-half peak).
Raw runs, outliers and metadata: `results/local/L-802a.json`. **No default changed** (allocator, `MALLOC_ARENA_MAX`,
`src/memplan.rs`, README formula); the owner decides.

## Root cause

- **No leak.** heaptrack, restore c8 l5000: peak heap 183.9 MB at 100k and 184.6 MB at 1M, flat per decile (164–174 MB),
  91 leaked allocations (26 KB) at both sizes, while RSS went 248 → 367 MB. The growth is **glibc malloc retention**:
  buffers are allocated on worker threads and freed on sink threads, and glibc's dynamic mmap threshold rises after the
  first large free (up to 32 MB), so later multi-MB buffers land in per-thread arenas and stay resident.
  `MALLOC_MMAP_THRESHOLD_=131072` pins the threshold and RSS goes flat; musl's mallocng behaves the same way.
- **Copy** heap grows 158 → 246 MB and then plateaus mid-run: scroll pages (`extract.rs`) waiting in the bounded
  processed channels (capacity `bufferSize`). At 100k (20 pages) the queues never fill; at 1M they do (15 → 90 MB live;
  `--bufferSize=4` gives 30 MB). Bounded, not a leak, so copy is never within 10% of 100k with any allocator.
- **Code fix (buffers that never shrink):** the JSON input splitter (`ValueSplitter.buf`) and the `--sourceOnly` file sink
  scratch buffer kept their largest capacity forever after one outsized document. New `release_excess()` shrinks a reused
  buffer to max(4 MiB, 2× its length) when its capacity is more than twice that. Unit tests
  `buffer_capacity_is_given_back_after_a_large_document` (32 MiB doc, then small docs: capacity ≤ 8 MiB) and
  `release_excess_leaves_normal_buffers_alone`. It does not change these benchmarks (no doc above 4 MiB).

## Architectures

Optional features `jemalloc` (tikv-jemallocator 0.7) and `mimalloc` (mimalloc 0.1, default features off); the default
build is unchanged and enabling both is a compile error. Verified with `cargo zigbuild` on the release toolchain
(1.85.1, `--locked`, LTO off), each with no feature, `jemalloc` and `mimalloc` (12 builds, all OK), and each binary ran a
20k-doc file → file round trip (all 20000 lines, exit 0; aarch64 under qemu-aarch64 user mode):

| Target | default | jemalloc | mimalloc |
|---|---|---|---|
| x86_64-unknown-linux-gnu | ok | ok | ok |
| x86_64-unknown-linux-musl (release target) | ok | ok | ok |
| aarch64-unknown-linux-gnu | ok | ok | ok |
| aarch64-unknown-linux-musl (release target) | ok | ok | ok |

x86_64-musl was also built for all three in the Dockerfile's DHI Alpine builder (rustc 1.99.0); jemalloc there needs
`make` (`apk add make perl`). Not verified: native arm64 image builds, the Debian glibc image builders, and aarch64
kernels with 16K/64K pages (jemalloc built for 4K pages can fail there, see `JEMALLOC_SYS_WITH_LG_PAGE`; mimalloc reads
the page size at run time).

## Recommendation (owner decides; nothing changed)

- Speed does not pick a winner: restore and copy run at the same rate with every allocator; only plain dumps are
  15–20% slower on musl and with `MALLOC_MMAP_THRESHOLD_=131072`.
- Lowest and flattest memory: the shipped musl build and glibc + `MALLOC_MMAP_THRESHOLD_=131072` (restore +2% / +4% from
  100k to 10M, the only cells inside the 10% goal; dumps ~20 MB). Keep musl's allocator for the release binaries and the
  default image: switching them to mimalloc would raise memory 2.3× (restore), 1.9× (copy) and 7× (dump).
- mimalloc is the best compiled-in allocator: same speed, flat from 1M to 10M (restore +9%, copy +8%), and 30–39% below
  glibc's default on restore/copy at 10M, on all four targets. It costs more than glibc on dumps (131 vs 75 MB,
  sliced 212 vs 165 MB) and about twice what musl or the mmap threshold use. jemalloc keeps growing and carries the
  aarch64 page-size risk.
- For glibc builds: `MALLOC_MMAP_THRESHOLD_=131072` (env, or `mallopt` at start) is the cheapest and lowest-memory option;
  `--features mimalloc` if the owner prefers one compiled-in allocator whose behaviour does not depend on the libc or the
  environment. Both beat `MALLOC_ARENA_MAX=2`, which still grows (+66% restore at 10M).
- Copy never meets "within 10% of 100k" (bounded queue warm-up); a 1M → 10M or plateau criterion passes for every
  variant except glibc default and jemalloc.
