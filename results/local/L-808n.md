# L-808n: restore CPU profile (owner request 2026-11-14)

Setup: 100,000-doc NDJSON file (`data100k.json`) restored into a local ES 8.19 (1 shard, 0 replicas,
isolated podman store) with `--limit 5000 --concurrency 4 --noRefresh --quiet`. CPU and peak RSS from
`getrusage(RUSAGE_CHILDREN)`; 6 reps per build, interleaved. Release builds with line tables.

| Build | user s (median) | sys s | CPU s (median) | wall s | peak RSS |
|---|---|---|---|---|---|
| M6 `704641c` (elasticdump-rs) | 0.30 | 0.14 | 0.45 | 1.25 | ~113 MB |
| main before (`8bcc92c`) | 0.64 | 0.16 | 0.80 | 1.31 | ~280 MB |
| main + L-808n | 0.48 | 0.13 | 0.61 | 1.37 | ~280 MB |

Result: restore CPU -24% (user -25%) vs main; wall time unchanged (ES-bound on this host); RSS unchanged.
Still about 1.35x M6 CPU and 2.5x M6 RSS.

## Profile (perf, before)
- 25.5% `BulkSink::process_batch` closure: byte-by-byte newline split plus the per-line nesting-depth scan (`too_deep`).
- 20.7% `json_split::ValueSplitter::next_value` (file input splitter).
- 21.8% `sonic_rs::Parser::skip_one` (two call sites: doc-line validation in `check_doc_line` and `encode_doc`).
- 8.2% memmove, 6.0% `Sink::write_all` closure (same byte split).

## Change (low risk, no behaviour change)
- `bulk::nonempty_lines`: memchr-based line iterator, used by `process_batch`, `write_batch`, `Sink` and `FileSink`
  (same lines as `split(b'\n').filter(non-empty)`; unit test incl. CRLF/blank/trailing cases).
- `too_deep` shortcut: depth can never exceed the count of `[`/`{` bytes, so a SIMD count of at most `max`
  skips the byte scan (verdict identical; unit test).

After: `process_batch` dropped out of the top entries. Remaining hot spots: kernel `clear_page_erms` 24% (page
faults from the larger RSS), `next_value` 16%, sonic `skip_one` 17%, copy-to-user 9%.

## Next candidates (not done; for the owner)
