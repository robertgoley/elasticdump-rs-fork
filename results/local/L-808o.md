# L-808o/p/q: next restore CPU fixes (owner approval 2026-11-14, t85u)

The three candidates from results/local/L-808n.md, one commit each, behaviour unchanged. Same setup as L-808n:
100,000-doc NDJSON restore into the local ES 8.19 (1 shard, 0 replicas), `--limit 5000 --concurrency 4
--noRefresh --quiet`, CPU and peak RSS from `getrusage`, interleaved reps, medians. The host was quieter than
during L-808n, so each step is compared with the previous build measured in the same session.

## L-808o: validate each document once

Before: `check_doc_line` ran a full `sonic_rs::from_slice::<IgnoredAny>` and then `encode_doc` walked the line again
with the checked object iterator (`Top::parse`): two `skip_one` passes over every document.

After: `check_and_parse` does one checked object-iterator pass that also confirms only `[ \t]* } [ \t]*` follows
the last value (what the full parse required), then the escape check, and hands the parsed members to the encoder.
Any line that pass is unsure about goes through the old two calls, so verdicts and messages are unchanged.
`check_and_parse_matches_the_two_pass_path` compares verdict, message and members against the old path on 28 seeds
plus about 10,000 byte-level mutations. `encode_doc` (retries, fuzz API) is unchanged.

| Build (6 reps each) | user s | CPU s | wall s | peak RSS |
|---|---|---|---|---|
| L-808n `b158898` | 0.42 | 0.545 | 1.20 | ~270 MB |
| L-808o | 0.37 | 0.47 | 1.17 | ~280 MB |

CPU -14%, user -12%; wall and RSS within noise.

## L-808p: fewer batch copies and reallocations

Before: `process_batch` copied every encoded batch (`encoded`) into a fresh `body` buffer before sending, and the
file reader grew each new batch buffer from empty by doubling (a new allocation and full copy per step), so every
batch touched several freshly zeroed buffers (kernel `clear_page_erms` was 24% in the L-808n profile).

After: chunk boundaries are computed from the encoded lengths (same `--maxBulkBytes` split rule), and a chunk that is
the whole batch (the common case) moves `encoded` into the request instead of copying it; a split batch still copies
its ranges. The file reader starts each batch buffer at the previous batch's size.

| Build (6 reps each) | user s | CPU s | wall s | peak RSS |
|---|---|---|---|---|
| L-808o | 0.38 | 0.515 | 1.23 | ~281 MB |
| L-808p | 0.36 | 0.455 | 1.20 | ~234 MB |

CPU -12% (mostly sys), peak RSS -17%; wall within noise.

## L-808q: faster input splitter

Before: `ValueSplitter::next_value` (file input: NDJSON, concatenated or pretty JSON) looked at every byte in a
`match` state machine (16-21% of restore CPU in the profiles).

After: inside a value it jumps straight to the next byte that can change its state: SIMD `memchr2` for `"`/`\`
inside strings, a 256-entry table for `"{}[]` outside them; that byte then goes through the unchanged byte-by-byte
code, so values, errors, size limits and buffering are identical. A proptest
(`skipping_scan_equals_byte_scan`, 10k cases, arbitrary also malformed bytes, random chunking and `--maxDocMb`
limits) compares every value, error and end state with the byte-by-byte scan; it fails if the table misses `]`.

| Build (6 reps each) | user s | CPU s | wall s | peak RSS |
|---|---|---|---|---|
| L-808p | 0.38 | 0.475 | 1.18 | ~248 MB |
| L-808q | 0.265 | 0.355 | 1.15 | ~252 MB |

CPU -25%; wall and RSS within noise.

## Overall (same session, 3 reps each)

| Build | CPU s | wall s | peak RSS |
|---|---|---|---|
| M6 `704641c` | 0.39 | 1.12 | ~106 MB |
| main before L-808n (`8bcc92c`) | 0.70 | 1.19 | ~282 MB |
| L-808n | 0.54 | 1.19 | ~270 MB |
| L-808q (o+p+q) | 0.355 | 1.15 | ~250 MB |

Restore CPU is now about half of what it was before L-808n and slightly below M6; wall time on this host is
bound by ES. Peak RSS is about 12% lower than before L-808n but still about 2.4x M6 (larger batch buffers and
allocator retention; the next lever would be the `write_batch` copy of each batch for `--concurrency` > 1, which
needs an owned-buffer API through `Sink`, and mimalloc purge settings; not done).
