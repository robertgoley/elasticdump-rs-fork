# L-807: LOAD-010 concurrency curves (Phase A, 1M docs on the box)

Setup: es717-plain 7.17.29 (2 GB heap, no CPU cap on the container), with 8 vCPUs that are shared with other work.
The data is 1,000,000 `load-logs` docs (edgen `logs`, seed 1, about 1 KB each, 1,012 MB NDJSON) on two indexes:

- `load-logs`: 1 primary shard.
- `load-logs-4sh`: a `_split` copy with 4 shards.

Both were force-merged to one segment per shard. The run used `scripts/load/curves.py L1L --reps 3` with
limit 1000, and points shuffled within each rep.

Each figure is the median of 3 runs:

- **CPU-s** is the tool's own CPU, from wait4.
- **server CPU-s** is the engine's process tree, background merges included.
- **gate Δ** comes from a second, independent 3-rep run checked against this run as the baseline.

**Result: PASS.** Two runs of 90 each, and all 180 exited 0 with the full doc count. On the first rep, all 30 dumps
and restores were digest-equal (60 across the two runs). No scroll contexts were left open. The regression gate
found 0 points more than 10% worse; deltas ranged from −5.3% to +10.5%.

## Regression gate (TST-LOAD-010: a drop of more than 10% at any point fails)

- **Second run against the baseline:** 0 regressions. Deltas ranged from −5.3% to +10.5%.
- **Negative check:** an L0 run (points 1 and 4) against a baseline with point 4 doubled exited 1, and all three point-4
  cells were flagged. The 1-rep L0 PIT point at 1 slice was also flagged, at −15.3%. Those runs take 0.9 s, so this
  is noise: the gate needs L1L, with 3 reps, on this box.

## Findings for the lead (no code change)

- **The curves are bound by the engine, not the tool.** The tool's CPU stays flat whatever the concurrency: 4.0–4.9
  CPU-s per 1M docs for dumps and 7.4–8.0 for restores.
- **PIT scales well.** It reaches 4.2–4.4× at 16 slices (about 500k docs/s) on both 1 and 4 shards. Scroll scales only
  until the slice count reaches the shard count (4 on 4 shards: 3.19×, about 410k docs/s).
- **Slicing a scroll past the shard count is a trap.** On 1 shard, every `--slices` value from 2 to 16 is slower than
  unsliced and costs 5–15× the server CPU. On 4 shards, 8–16 slices fall back to about 1.7×.
  - This matches the README guidance.
  - A warning when a scroll dump has more `--slices` than primary shards could be considered, but that is the lead's
    call, so I didn't add one.
- **Restore levels off above concurrency 8.** It reaches 4.05× at 8 and 4.5× at 16 (about 85k docs/s). Above 8 the
  engine is CPU-saturated, with about 6.8 of the 8 shared vCPUs busy.
- **The box is too noisy for B10's standard.** 10 of 30 points have a CV above 5% (the worst is 15.1%), and B10 needs a
  CV below 5% at every point. So these curves are trends only.
