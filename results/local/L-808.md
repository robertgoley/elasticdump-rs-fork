# L-808: LOAD-011 Node comparison (Phase A, 100k and 1M docs on the box)

Setup: es717-plain 7.17.29 (no CPU cap on the container) on 8 vCPUs that are shared with other work. The data is
edgen `logs` (seed 1, about 1 KB per doc) in a 2-shard `_split` copy, force-merged. Node is elasticdump 6.125.1 on
node v24.22.1, installed with `--ignore-scripts`; only its CLI was run, never npm. Rust is the release build.
The run used `scripts/load/nodecmp.py <tier> --reps 3` with scenarios shuffled and the two tools shuffled within each rep.
Figures are medians of 3 runs. CPU-s and RSS are from wait4.

**Result: PASS** (TST-LOAD-011: ratios recorded, digests equal). 2 × 39 runs, all exit 0. On the first rep:

- Every dump is digest-equal to the index.
- Every Node output is digest-equal to every Rust output for the same scenario (5 checks per tier).
- Restore and copy targets are digest-equal to the source.

elasticdump-rs left no scroll context open after any run. Node left 2 per scroll dump (one per shard), and they
stay open until `scrollTime` expires.

## PLAN.md §8 targets (reported, not asserted)

| target | 100k | 1M | met? |
|---|---|---|---|

| ES→ES ≥ 2.5× | 1.61× | 1.30× | no (engine-bound) |
| `--fsCompress` ≥ 150 MB/s per core | – | 200 MB/s codec CPU (112 MB/s of all tool CPU; 159 MB/s wall) | yes, measured as in L-805 |
| CPU ≥ 3× fewer CPU-s | 3.75–5.53×, copy 2.71× | 3.39–5.46×, copy 2.52× | all but copy |

Why restore and copy miss: Node uses about 1.08 cores, so it is CPU-bound. elasticdump-rs uses 0.47–0.56 of a core
and waits on the single engine node, which shares the 8 vCPUs with both tools. L-807 showed the same engine reaching
85k docs/s only at `--concurrency 16`. The defaults case (limit 100) is round-trip bound for Rust (15 s of wall
for 5.5 CPU-s). These targets need a multi-node engine on dedicated cores (Phase B).

Most cells are outside ±20%, so **the README Performance table was replaced** with the measured medians, the CPU

added. The pre-rewrite "Upstream benchmark" section was left as is. It is labelled `b32b6e9` on a 32-core host and
can't be reproduced here. Its ratios are close to this run's: unsliced 1.6–2.0× against our 1.63–1.84×, and
scroll `--slices 2` 3.77× against our 3.51–3.85×.

## Finding: Rust CPU has risen since M6 (no change in L-808)

Restore and copy CPU-s are about 2× the old README figures. To check that this is real and not noise, I ran a
Rust-only A/B after the gates finished. Setup: OpenSearch 2.19.7, the quick-vs-node data, 9 interleaved runs per cell,
release builds:

| median CPU-s (min–max) | M6 `704641c` | L-633 `c042e0c` | head `e9d8cc5` |
|---|---|---|---|
| restore | 0.223 (0.218–0.235) | 0.418 (0.404–0.466) | 0.442 (0.421–0.46) |
| copy | 0.243 (0.233–0.256) | 0.535 (0.5–0.552) | 0.507 (0.485–0.571) |
| dump `--limit 5000` | 0.134 (0.126–0.156) | 0.192 (0.184–0.213) | 0.189 (0.179–0.224) |

The ranges don't overlap, so the increase is real. An earlier 5-run A/B gave the same result. Wall time is only
4–14% slower, because the engine is the bottleneck. The increase is already present at L-633.

**I don't know which commit caused it.** A `git bisect run` (3 runs per step, not interleaved, fixed 0.36 CPU-s
threshold) named `3e5a706` (L-618). That commit only touches `tests/it`, so it can't change the binary: the result is
a false positive from noise. Its L-633 sample read 0.308, against 0.418 in the 9-run A/B.

`perf` on the head restore shows these hot spots:

- sonic_rs `skip_one`: about 27%
- `ValueSplitter::next_value`: 12%
- `bulk::check_doc_line`: 9%
- `get_from_object`: 5%

This is a hint, not an attribution, because M6 wasn't profiled. The tool still uses ≥ 3× less CPU than Node
everywhere except copy.

For the lead: bisect `704641c..c042e0c` with interleaved runs, then decide whether the cost is intended.
