## Checks

- **Independent decoding:** every f2f and dump output decodes to the uncompressed bytes. gzip was checked with
  gzip(1) and zstd with Python zstandard 0.25.
- **Read-back:** the tool reads each output back byte for byte, and every dump is digest-equal to the index
  (edverify).
- **Parts** (`--fileSize 64mb`, gzip 6 and zstd 3, 16 parts each):
  - `cat` of the parts decodes to the reference bytes.
  - The tool reads the cat'ed file back to the reference bytes.
  - Each part decodes on its own.

## Findings for the lead (no code change)

- **gzip 9 is not worth using with zlib-rs.** The zlib-rs backend's level 9 makes a 3.5% *larger* file than level 6;
  stock zlib's level 9 is 5% smaller. It also costs 65% more CPU. Level 1 makes a file 25% larger than stock zlib's
  level 1, but runs at about 1.1 GB/s per core. Both were cross-checked on 200k docs against gzip(1) and Python zlib.
- **zstd 3 is slightly larger than zstd 1** on this corpus.
- **zstd 19 is impractical at scale.** It runs at about 1.8 MB/s per core, single-threaded.
- **Default levels cost no dump time.** Dumps are bound by the cluster, so gzip 1/6 and zstd 1/3 add no wall time;
  levels 9 add 30–40%.
- **Part naming matches Node.** Parts are named `p.split-N.json.gz` / `.zst`. An output named `p.json.gz` gives
  `p.json.split-N.gz.gz` in both tools, because the name comes from Node's generateFilePath.
