# Release-build performance evaluation

This is the entrypoint for measuring a **published searchdump-rs release** (or a
local directory of the same binaries) on a Linux server, using the same engine
images, seeders and cases as [`run-suite.sh`](run-suite.sh). Run it from a repo
checkout. Results land under `scripts/perf/results/release-eval/<version>/<hostid>/`
in a form you can commit and push (or open a PR) for evaluation.

The underlying timing and correctness protocol is unchanged: see [README.md](README.md).
searchdump-rs is provided as is, without warranty of any kind; see the disclaimer
in the top-level [README.md](../../README.md) and the [MIT license](../../LICENSE).

```bash
# Print the plan only: no downloads, image pulls, containers or result writes.
scripts/perf/release-eval.sh --dry-run
scripts/perf/release-eval.sh --preset quick --tag v1.0.0-beta1 --dry-run

# Quick two-engine check of a published tag (rootless podman, isolated store).
scripts/perf/release-eval.sh --preset quick --tag v1.0.0-beta1

# Full 16-engine L0 suite, also compare Node elasticdump 6.125.1, then commit
# only the results directory. Push stays opt-in (the command is printed).
scripts/perf/release-eval.sh --tag v1.0.0-beta1 --compare-node --reps 3 --commit

# Evaluate a local build instead of a GitHub archive.
scripts/perf/release-eval.sh --bin /path/to/release/bins --tag local --preset quick
```

`--tag` / `--version` defaults to the latest *published* GitHub release
(including a pre-release when that is all there is). Draft releases are not
downloadable anonymously; pass `--bin` or wait until the release is published.

## Requirements

- A **Linux** host. Rootless **podman** is the expected (and recommended) setup;
  no sudo is required. The driver never uses your default podman store: it
  creates an isolated store and `XDG_RUNTIME_DIR` under the run directory
  (`$XDG_CACHE_HOME/searchdump-rs/release-eval` by default, overridable with
  `--run-dir`).
- Python 3.11+, bash, curl, tar, sha256sum, git. `gh` is used when present;
  otherwise the GitHub HTTP API and curl are used. npm is needed only with
  `--compare-node`.
- Disk and RAM: preflight refuses a host with fewer than about 8 GiB free disk.
  OpenSearch 2 and 3 still use a 4 GiB heap for L0 `restore-big`, so a full run
  wants several gigabytes of free memory; the `quick` preset is lighter except
  that it includes `os3-plain`. `--dry-run` prints the per-engine estimate.
- Pinned engine and helper images from [`scripts/it/images.lock`](../it/images.lock)
  are pulled into the *isolated* store on first run (skip with `--skip-pull` if
  they are already there). These are the same images `run-suite.sh` uses:
  `es710`, `es717`, `elasticsearch8`, `es819`, `elasticsearch` (9), `os13`,
  `os2`, `os3`, each plain and secure, plus the Alpine/toxiproxy helpers.
- Network notes inherited from the suite: engine helpers use `--network=host`
  and **must not** combine that with `--userns=keep-id`. Engine ports are
  loopback-only. The default port is the first free port in 19242–19261 (or
  `PERF_ENGINE_PORT` / `--port`), so this driver stays out of the way of a
  default suite (19222) or an existing isolated run that already claimed a
  port. Only one suite holds `/tmp/searchdump-it.lock` at a time.
- A `STOP` file in the run directory pauses between engines. Per-engine
  `.done` markers make the same command resumable. Cleanup and orphan reaping
  (conmon / pasta) are limited to this run directory's store and runtime dir.

Release archives (`searchdump-rs-<version>-<target>.tar.gz`) contain
`searchdump` and `searchdump-multi` (and the compatibility symlinks). The
suite also needs `edgen` and `edverify` to seed data and check correctness;
those are built from *this checkout* when the archive does not include them.
The product binaries under test are never silently replaced by a checkout
build. Checksums (`.sha256` or `SHA256SUMS`) are verified when GitHub
provides them; `--allow-unverified` is required to accept an asset that has
none. The preferred archive is the host's `*-unknown-linux-gnu` build on
glibc (see the Releases section of the top-level README); musl is selected
automatically on a musl host, or pass `--target`.

`--bin DIR` skips the download and uses local `searchdump` and
`searchdump-multi` (and `edgen` / `edverify` if they are in that directory).

`--compare-node` is opt-in. It installs the suite's pinned **Node elasticdump
6.125.1** into the run directory with `npm ci --ignore-scripts` (the
lockfile under `scripts/perf/`), never into the repo tree.

Secure engines use the throwaway passwords already generated by
`scripts/it/up.sh`. Credentials are not written into the results directory.

## Presets and time

| Preset | Engines |
|---|---|
| `all` (default) | the full 16: es710, es717, elasticsearch8, es819, elasticsearch (9), os13, os2, os3 × plain and secure |
| `quick` | `es819-plain`,`os3-plain` |
| `plain` | the eight `*-plain` profiles |
| `secure` | the eight `*-secure` profiles |

`--engines` takes a comma-separated list of those same ids (do not combine it
with `--preset`). `--cases`, `--tier` (default L0), `--place` (default `box`)
and `--reps` (default 3) are passed through to the suite. Dedicated hosts can
use `--place big`. `--host-id` overrides the generated id (hostname, arch,
cores and RAM).

Time is **rough** and host-dependent. The v1.0.0-beta1 L0 suite on a typical
dev box — all 16 engines, three repetitions, Node comparison included — took
**many hours** (individual engines often ran for a large fraction of an hour).
The `quick` preset is a much smaller fraction of that (two engines). Storage
speed, available RAM, and whether `--compare-node` is on all change the
total. `--dry-run` does not estimate a clock time.

## Results and how to submit them

Each run writes:

```
scripts/perf/results/release-eval/<version>/<hostid>/
  host-metadata.json   CPU, cores, RAM, kernel, distro, podman, disk kind,
                       and a best-effort cloud instance type (no secrets,
                       no instance ids, no tokens)
  plan.json            resolved tag, engines, preflight
  manifest.json        binary hashes/versions, checkout git, flags
  report.md            aggregate.py markdown summary
  engines/<engine>/    combined.json, summary.md, engine.json
  baselines/           only with --update-baselines
```

`--commit` runs `git add` on **that directory only** and `git commit --only`
with the message `perf: release-eval <version> results from <hostid>`. It
does not push. The script prints the push command, for example:

```bash
git push origin HEAD:main
```

`--push` is opt-in and runs that push after a successful commit. Prefer a
branch and a pull request if you do not maintain the destination branch:

```bash
git checkout -b release-eval/1.0.0-beta1/my-host
scripts/perf/release-eval.sh --tag v1.0.0-beta1 --commit
git push -u origin HEAD
# then open a PR
```

Please do not commit run-directory state (the isolated podman store, logs, or
downloaded archives). Only the results tree above is meant to be recorded.

## Related tools

- [`run-suite.sh`](run-suite.sh) / [`suite.py`](suite.py) — the per-engine
  suite this driver calls in `--host-tools` mode with `PERF_BIN_DIR` set.
- [`aggregate.py`](aggregate.py) — builds `report.md` from the per-engine
  `combined.json` files.
- `python3 scripts/perf/selftest.py` — offline tests, including this driver's
  plan, checksum, fingerprint and commit helpers. Those tests do not start
  engines or pull images.
